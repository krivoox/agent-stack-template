# ADR-006 — Conventional Commits and generated releases

**Status:** Accepted

## Context

A changelog written by hand is written last, by whoever is shipping, from
memory. It drifts immediately. Version numbers picked by hand encode whatever
the person felt about the change rather than whether it breaks a consumer.

Both problems have the same root: the information needed already exists in the
commit history, but not in a machine-readable form.

## Decision

**Commit messages are the release input.**

- [Conventional Commits](https://www.conventionalcommits.org/), enforced by
  commitlint in the `commit-msg` hook. A bad message fails before it exists.
- `git-cliff` (`cliff.toml`) derives the changelog from the history.
- The version bump follows from the commit types: `fix:` → patch, `feat:` →
  minor, `BREAKING CHANGE:` / `!` → major.
- `CHANGELOG.md`'s `[Unreleased]` section is regenerated by CI on every push to
  `develop`, so the pending release is always visible.
- `scripts/release.mjs` cuts the release; `github-actions[bot]` is the only
  identity permitted to push the resulting commit to a protected branch.

Types in use: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`,
`build`, `ci`, `chore`, `revert`.

## Consequences

**Gained.** The changelog cannot drift from the history. The version follows
from the change, not from a mood. Reviewers see intent in the subject line.
Release is one command.

**Given up.** Contributors must learn a message format, and the hook will
reject them until they do. A change committed under the wrong type produces a
wrong bump — `feat` for a bug fix inflates the minor version, and the fix is a
new commit, not a rewritten history.

**Boundary.** The hook is local; CI must re-validate. Squash-merge titles are
what actually land on `develop`, so the PR title is the message that matters.
